## 테스트가 다 통과했는데 버그가 있다

AI 코딩 에이전트에게 기능과 테스트를 같이 맡기면, 대부분 초록색 결과를 들고 옵니다. "테스트 12개 모두 통과했습니다." 그런데 배포하고 나서 그 테스트가 지켜야 했던 바로 그 부분에서 버그가 나옵니다.

에이전트가 거짓말을 한 건 아닙니다. 테스트는 정말 통과했습니다. 문제는 **그 테스트가 아무것도 검사하지 않았다**는 것입니다.

이 글에서는 에이전트의 검증 결과를 믿기 전에 확인하는 다섯 가지 방법을 정리합니다. 예시는 모두 가상의 주문 관리 API입니다.

## 1. 새 단언은 일부러 깨 본다 (변이)

통과한 테스트가 근거가 되려면, **구현이 틀렸을 때 실패해야** 합니다. 이걸 확인하는 가장 빠른 방법은 구현을 일부러 망가뜨려 보는 것입니다.

예를 들어 "미리보기는 5분이 지나면 실행할 수 없다"는 테스트가 있다고 합시다.

```ts
it("만료된 미리보기는 실행할 수 없다", async () => {
  const plan = await preview(changeAddress(1024, "새 주소"));
  advanceTime(6 * 60 * 1000);
  await expect(execute(plan.id)).rejects.toThrow();
});
```

통과합니다. 이제 구현의 만료 검사를 지워 봅니다.

```ts
// if (now > plan.expiresAt) throw new ExpiredError();   ← 주석 처리
```

그래도 통과한다면, 이 테스트는 만료를 검사하지 않습니다. 실제로 돌려 보면 통과합니다. 이유는 `execute(plan.id)`에 **쓰기 권한 키를 넘기지 않아서** 만료와 상관없이 권한 오류가 났기 때문입니다. `toThrow()`가 **어떤 에러든** 받아 주니 그 사실이 가려졌습니다.

고치는 방법은 단언을 좁히는 것입니다.

```ts
await expect(execute(plan.id, WRITE_KEY)).rejects.toThrow(ExpiredError);
```

단언을 좁히면 키를 빠뜨린 실수도 바로 드러납니다. 권한 오류는 `ExpiredError`가 아니니 테스트가 실패하기 때문입니다.

직접 돌려 본 결과는 이렇습니다.

| | 원래 구현 | 만료 검사를 지운 구현 |
|---|---|---|
| 처음 테스트 (`toThrow()`, 키 없음) | 통과 | **통과** ← 아무것도 검사하지 않음 |
| 고친 테스트 (`toThrow(ExpiredError)`, 쓰기 키) | 통과 | **실패** ← 제대로 검사함 |
| "만료 전에는 실행된다" 테스트 | 통과 | 통과 |

**절차**: 새로 추가된 단언마다 → 그 단언이 지키는 구현 한 줄을 망가뜨림 → 테스트가 실패하는지 확인 → 되돌림. 에이전트에게도 이 절차를 그대로 시킬 수 있습니다.

## 2. 한 사례가 아니라 집합을 검증한다

"주문 상세 조회 API에서 다른 사람 주문이 보인다"는 이슈가 들어왔다고 합시다. 에이전트는 그 API에 권한 검사를 넣고, 테스트를 추가하고, "고쳤습니다"라고 보고합니다.

하지만 같은 데이터를 돌려주는 경로가 그것 하나뿐일까요?

- 목록 조회 API
- 검색 API
- 프레임워크가 기본으로 열어 주는 공통 CRUD 경로
- 엑셀 내보내기

이슈에 **지목된 사례 하나**를 고친 것과 **문제의 집합 전체**를 닫은 것은 다릅니다. 권한이나 데이터 노출 문제는 특히 그렇습니다.

**방법**: 코드를 읽어서 경로를 찾지 말고, **실제로 등록된 라우트 목록을 런타임에서 뽑아서** 전부 검사합니다. 상속이나 프레임워크 기본값으로 생기는 경로는 코드 검색으로는 잘 안 보이기 때문입니다.

## 3. 관찰 도구부터 의심한다

에이전트가 이렇게 보고하는 경우가 있습니다.

> 로그를 검색해 보니 해당 에러는 0건입니다. 문제가 재발하지 않았습니다.

0건은 결론이 아닙니다. 먼저 이것부터 의심해야 합니다.

- 검색한 **로그 그룹이 맞나**: 같은 서비스라도 API 요청과 백그라운드 작업이 다른 곳에 로그를 남길 수 있습니다.
- **기간이 맞나**: 기본 검색 기간이 짧게 잡혀 있지 않나.
- **출력이 잘린 건 아닌가**: 도구가 앞부분만 보여 준 걸 전체로 착각하지 않았나.
- **검색어가 맞나**: 에러 메시지 형식이 바뀌지 않았나.

"없다"고 말하려면, **있었다면 반드시 보였을 곳을 봤다는 근거**가 필요합니다. 이력이나 다른 경로로 한 번 더 확인합니다.

## 4. 정상 경로의 거절은 설명하지 말고 고친다

에이전트가 테스트 중에 4xx 응답을 받고 이렇게 설명하는 경우가 있습니다.

> 테스트 계정에 데이터가 없어서 400이 난 것으로 보입니다. 정상 동작입니다.

정상적인 사용자가 정상적인 순서로 요청했는데 거절당했다면, 그건 대부분 **계약(API 스펙)이나 구현의 결함**입니다. "데이터 탓", "환경 탓"으로 설명하고 넘어가는 순간 버그가 사라지지 않고 숨습니다.

**규칙**: 정상 경로에서 거절이 나면, 원인이 확인될 때까지 결함으로 취급합니다.

## 5. 숫자에는 분모를 붙인다

"수정 후 오류가 3건으로 줄었습니다"라는 보고는 아무것도 말해 주지 않습니다.

- 몇 건 중 3건인가?
- 어떤 기간, 어떤 대상에서 셌나?
- 같은 결과를 내가 다시 볼 수 있는 명령은?

에이전트에게 결과를 보고받을 때는 **모집단, 분모, 재현 명령**을 같이 요구합니다. 이 세 가지가 없으면 숫자를 검증할 수 없고, 검증할 수 없는 숫자는 근거가 아닙니다.

## 에이전트에게 이렇게 시킨다

위 다섯 가지는 에이전트 지시문으로 그대로 옮길 수 있습니다.

```text
검증 규칙:
1. 새로 추가한 단언마다, 그 단언이 지키는 구현을 일부러 망가뜨려 실패하는지 확인하고 되돌린다. 결과를 보고한다.
2. 권한·노출 문제는 지목된 경로만이 아니라, 런타임에 등록된 전체 경로를 뽑아 검사한다.
3. "없다"고 보고하려면 어디를, 어떤 기간으로, 어떤 검색어로 봤는지 함께 적는다.
4. 정상 경로에서 거절이 나면 결함으로 보고한다. 환경·데이터 탓으로 설명하지 않는다.
5. 숫자에는 모집단, 분모, 재현 명령을 붙인다.
```

더 확실하게 하려면 이 검증을 별도 에이전트(QA 리뷰어)에게 맡깁니다. 구현한 에이전트가 자기 결과를 검증하면 같은 맹점을 공유하기 때문입니다.

## 정리

| 확인 | 질문 |
|---|---|
| 변이 | 구현이 틀리면 이 테스트가 실패하는가? |
| 집합 | 지목된 한 곳이 아니라 전체를 닫았는가? |
| 관찰 도구 | "없다"는 결과를 낸 도구가 제대로 봤는가? |
| 정상 경로 거절 | 설명하고 넘어가지 않았는가? |
| 분모 | 이 숫자를 내가 다시 잴 수 있는가? |

통과한 테스트는 시작점일 뿐입니다. 에이전트가 빨라질수록, 그 결과를 **믿지 않고 확인하는 구조**를 먼저 만들어 두어야 합니다.
