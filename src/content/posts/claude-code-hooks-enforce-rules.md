## 규칙을 적었는데 또 어긴다

Claude Code를 팀에서 쓰다 보면 비슷한 일을 반복해서 겪습니다.

- `CLAUDE.md`에 "커밋 전에 테스트를 돌린다"고 적었는데, 바쁜 작업 중에 테스트 없이 커밋합니다.
- 메모리에 "운영 환경에는 쓰지 않는다"고 남겼는데, 긴 디버깅 끝에 운영 API를 호출하려 합니다.
- 같은 실수를 지적하면 "앞으로 지키겠습니다"라고 답하고, 다음 세션에서 또 어깁니다.

처음에는 규칙을 더 눈에 띄게 쓰거나, 더 위에 두거나, 굵게 표시했습니다. 효과가 없었습니다.

## 원인: 검색 문제가 아니라 강제 문제

규칙이 안 지켜지는 이유를 "모델이 규칙을 못 찾아서"라고 생각하기 쉽습니다. 하지만 대부분은 규칙이 컨텍스트에 **들어와 있는데도** 어깁니다.

- `CLAUDE.md`와 메모리는 **참고 자료**로 컨텍스트에 들어갑니다. 강제력이 없습니다.
- 작업이 길어지면 당장 눈앞의 목표("이 버그를 고친다")가 오래전에 읽은 규칙보다 앞섭니다.
- 규칙이 많아질수록 각각의 무게는 줄어듭니다.

그래서 규칙을 더 잘 쓰는 것으로는 해결되지 않습니다. **지켜야만 하는 규칙은 모델의 판단에 맡기지 말고 기계가 막아야 합니다.**

## 1단계: 기계로 옮길 규칙을 고른다

모든 규칙을 훅으로 만들 필요는 없습니다. 이런 규칙만 고릅니다.

| 기준 | 예 |
|---|---|
| 되돌리기 어려운 행위 | 커밋·푸시, 운영 배포, 데이터 삭제, 외부 발송 |
| 두 번 이상 어긴 규칙 | "테스트 없이 커밋했다"가 반복될 때 |
| 판단이 아니라 조건으로 말할 수 있는 규칙 | "게이트 기록이 없으면 커밋 불가"처럼 참·거짓이 분명한 것 |

"코드를 깔끔하게 쓴다"처럼 판단이 필요한 규칙은 훅이 아니라 리뷰 에이전트의 몫입니다.

## 2단계: 훅으로 막는다

Claude Code의 `PreToolUse` 훅은 도구가 실행되기 **직전에** 호출됩니다. 훅이 종료 코드 2로 끝나면 그 호출은 막히고, 훅이 stderr에 쓴 내용이 Claude에게 전달됩니다. Claude는 "왜 막혔는지"를 읽고 다음 행동을 바꿉니다.

예를 들어 "품질 게이트를 통과한 기록이 없으면 커밋할 수 없다"는 규칙은 이렇게 만듭니다.

`.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/require-gate.sh" }]
      }
    ]
  }
}
```

훅 경로는 `$CLAUDE_PROJECT_DIR` 기준으로 적습니다. 상대 경로로 적으면 Claude가 `cd`로 다른 폴더에 들어간 뒤에는 훅 스크립트를 찾지 못합니다.

```bash
#!/usr/bin/env bash
# .claude/hooks/require-gate.sh
cmd=$(jq -r '.tool_input.command // ""')

# git commit 이 아니면 통과 (git 과 commit 사이에 -C·-c 같은 옵션이 끼어도 잡는다)
echo "$cmd" | grep -qE '(^|[;&|[:space:]])git([[:space:]]+[^;&|]*)?[[:space:]]commit([[:space:]]|$)' || exit 0

# 지금 스테이징된 내용에 대한 게이트 기록이 있는지 확인
tree=$(git write-tree)
if [ ! -f ".gate/$tree.pass" ]; then
  echo "커밋 차단: 스테이징된 변경($tree)에 대한 게이트 기록이 없습니다. 먼저 품질 게이트를 실행하세요." >&2
  exit 2
fi
```

핵심은 **기록을 스테이징된 내용에 묶는 것**입니다. 게이트를 통과한 뒤 파일을 하나 더 고치면 트리 해시가 바뀌어서 다시 막힙니다. "게이트 한 번 돌리고 계속 고치기"가 불가능해집니다.

### 직접 돌려 본 결과

빈 저장소에 파일 하나를 스테이징하고, 훅에 여러 명령을 넣어 봤습니다.

| 명령 | 결과 |
|---|---|
| `git status` | 통과 |
| `git commit -m x` | 차단 |
| `cd sub && git commit -m x` | 차단 |
| `echo "git commit"` | 통과 (문자열일 뿐이라 정상) |
| `git -C . commit -m x` | 차단 |
| `git -c user.name=x commit -m x` | 차단 |
| 기록을 만든 뒤 `git commit -m x` | 통과 |
| 기록을 만든 뒤 파일을 더 스테이징하고 `git commit -m x` | 차단 |

스크립트만 따로 돌린 게 아니라, 실제 Claude Code(2.1.332)에 이 훅을 걸고 커밋을 시켜 봤습니다. 기록이 없을 때는 호출이 막혀 커밋이 생기지 않았고, 훅이 stderr에 쓴 차단 문구가 Claude에게 그대로 전달됐습니다. 기록을 만든 뒤에는 같은 요청으로 커밋됐고, 파일을 더 스테이징하자 다시 막혔습니다.

처음 쓴 패턴(`git[[:space:]]+commit`)은 `git -C . commit`과 `git -c ... commit`을 **그냥 통과시켰습니다.** 옵션이 끼면 못 잡았던 것입니다. 위 코드는 고친 패턴입니다. 훅을 만들면 이렇게 **빠져나갈 수 있는 명령을 직접 넣어 보는 것**까지가 한 세트입니다.

고친 패턴에도 한계가 있습니다.
- `git log --grep commit`처럼 커밋이 아닌 명령도 막습니다. 막는 쪽으로 틀리는 건 안전하니 그대로 둡니다.
- `git -C 다른폴더 commit`이면 게이트 기록은 **현재 폴더** 기준으로 확인합니다. 여러 저장소를 오가는 환경이면 `-C` 경로를 읽어서 그 저장소 기준으로 확인하도록 보강해야 합니다.

### 함정: 훅은 Bash 호출 전체를 막는다

훅은 명령 한 줄이 아니라 **Bash 호출 하나 전체**를 판단합니다. `기록 남기기 && git commit`처럼 묶으면 커밋 때문에 호출 전체가 막혀서 기록도 남지 않습니다. 막힐 수 있는 명령은 다른 명령과 묶지 않도록 규칙에 함께 적어 두세요.

## 3단계: 규칙에는 출처를 남긴다

규칙이 쌓이다 보면 "이건 왜 있지?" 싶은 규칙이 생깁니다. 출처가 없는 규칙은 지워도 되는지 판단할 수 없고, 결국 모두 남아서 서로의 무게를 깎습니다.

규칙마다 세 가지를 적습니다.

- **누가** 정했나: 사용자 지시인지, 모델이 추론한 것인지
- **언제, 무슨 일로** 생겼나: 어떤 사고나 지적에서 나왔는지
- **얼마나 확실한가**: 확정인지, 후보인지

모델이 스스로 추론해서 만든 규칙은 사람이 확인하기 전까지 "후보"로 둡니다. 출처 없는 규칙은 규칙이 아닙니다.

## 4단계: 인용 금지가 아니라 행위 금지

시크릿 관련 규칙을 예로 들면, 처음에는 이렇게 쓰기 쉽습니다.

> 시크릿 값을 출력하지 마라.

하지만 모델은 값을 출력하려는 게 아니라 **확인하려다가** 출력합니다. 설정을 복호화하고, 결과를 화면에 찍고, 그다음에야 "아, 출력하면 안 되지"가 됩니다. 이미 늦었습니다.

그래서 규칙의 대상을 결과(인용)가 아니라 **행위**로 옮깁니다.

> 시크릿을 복호화하는 명령을 실행하지 않는다. 키 이름이 필요하면 키 이름만 뽑는다.

그리고 이것도 훅으로 막습니다. 복호화 명령 패턴이 보이면 호출 자체를 차단합니다.

## 정리

- 규칙이 안 지켜지는 건 대부분 **찾지 못해서가 아니라 강제력이 없어서**입니다.
- 되돌리기 어렵고, 반복해서 어기고, 조건으로 말할 수 있는 규칙만 골라 **훅으로 막습니다.**
- 통과 기록은 **스테이징된 내용에 묶습니다.**
- 규칙에는 **출처**를 남기고, 출처 없는 규칙은 지웁니다.
- 규칙은 결과가 아니라 **행위**를 금지합니다.

다음 글에서는 이렇게 막아 둔 게이트 안에서, 에이전트가 만든 "통과한 테스트"를 어떻게 믿지 않고 검증하는지 다룹니다.
